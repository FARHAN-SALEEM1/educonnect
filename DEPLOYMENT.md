# Deploying EduConnect

Three routes, easiest first. All of them need the same four things: a Postgres database, the API, the static frontend, and a set of real secrets.

---

## Before anything else — generate secrets

Run this twice and keep the two values apart:

```bash
node -e "console.log(require('crypto').randomBytes(48).toString('hex'))"
```

One becomes `JWT_ACCESS_SECRET`, the other `JWT_REFRESH_SECRET`. They must differ.

The API **refuses to start** with `NODE_ENV=production` if either secret is missing, shorter than 32 characters, still the `change_me…` placeholder, or if both are identical. That check exists because those defaults are exactly what survives a rushed deploy.

---

## Option 1 — Docker Compose (one machine, one command)

Best for a demo, a college server, or a single school on one VPS.

```bash
cp backend/.env.example .env
```

Edit `.env` at the repo root so it has at least:

```
DB_PASSWORD=<a long random string>
JWT_ACCESS_SECRET=<48-byte hex>
JWT_REFRESH_SECRET=<a different 48-byte hex>
```

Then:

```bash
docker compose up --build
```

```bash
docker compose exec api npm run db:seed
```

- App → <http://localhost:8080>
- API → <http://localhost:5001>

Migrations run automatically on start. Postgres is published on host port **5433** so it doesn't collide with a local install.

> Only seed a database you're happy to erase — `db:seed` clears the tables it owns.

---

## Option 2 — Managed platforms (free tier, no server to run)

The usual choice for an FYP: a public URL, nothing to maintain.

### 1. Database — [Neon](https://neon.tech)

Create a project, copy the connection string. It looks like:

```
postgresql://user:pass@ep-xxx.aws.neon.tech/neondb?sslmode=require
```

### 2. Push the repo to GitHub

Render deploys from a Git remote, so the code has to be on GitHub first. This repo is already initialised and committed locally.

Create an **empty** repo on GitHub (no README, no .gitignore — this one has both), then:

```bash
git remote add origin https://github.com/<you>/educonnect.git
```

```bash
git branch -M main && git push -u origin main
```

### 3. Both services — [Render](https://render.com)

**New → Blueprint → select your repo.** Render reads [`render.yaml`](render.yaml) and creates the API and the frontend together, so there are no build or start commands to type by hand.

It prompts for the values marked `sync: false`:

| Prompt | What to enter |
|---|---|
| `DATABASE_URL` | Your Neon connection string, including `?sslmode=require` |
| `CORS_ORIGIN` | The frontend URL — see the ordering note below |
| `APP_URL` | Same as `CORS_ORIGIN` |
| `VITE_API_URL` | The API URL + `/api` |
| `SMTP_*` | Leave blank unless you have a mail server |

The JWT secrets are **generated by Render** — you never pick or paste them.

#### The ordering problem

Each service needs the other's URL, and neither exists until it deploys. Render's default names are predictable:

- API → `https://educonnect-api.onrender.com`
- Frontend → `https://educonnect-web.onrender.com`

Enter those when prompted. If Render appends a suffix because a name is taken, correct the values under each service's **Environment** tab and redeploy. `VITE_API_URL` is inlined at build time, so it needs a **rebuild**, not just a restart.

`COOKIE_CROSS_SITE=true` is already set in the blueprint, and it matters: the refresh token is an httpOnly cookie, and the API and frontend are different origins on Render, so it needs `SameSite=None; Secure`. Without it, login succeeds and the session vanishes on the very next request.

`/health` returns **503** when the database is unreachable, so Render stops routing traffic to a broken instance rather than serving errors.

### 4. Seed once

From your machine, pointing at the production database:

```bash
cd backend && DATABASE_URL="<your Neon string>" npm run db:seed
```

Then **immediately change every demo password**, or delete the demo accounts and create your own. The seeded logins are published in this repo's README.

> On Render's free tier the API sleeps after ~15 minutes idle, so the first request after a pause takes 30–50 seconds. Fine for a demo — just open the page a minute before you present.

## Option 3 — Your own VPS

Build the two images from `backend/Dockerfile` and `frontend/Dockerfile`, run them behind nginx or Caddy with TLS, and point `DATABASE_URL` at a managed Postgres or one you run yourself. `app.set("trust proxy", 1)` is already set, so client IPs and rate limiting work correctly behind a reverse proxy.

## Email

**Production will not start without SMTP.** Locally, leaving `SMTP_HOST` blank
prints password-reset links and welcome emails to the server console instead of
sending them, which is fine for a demo. In production that fallback is a
failure: nobody could ever reset a password, and live reset tokens would sit in
your log aggregation for anyone with log access to use. So the startup check
refuses to boot when `SMTP_HOST` or `SMTP_FROM` is missing and
`NODE_ENV=production`.

Set:

```
SMTP_HOST=smtp.resend.com
SMTP_PORT=587
SMTP_USER=resend
SMTP_PASS=<your API key>
SMTP_FROM="Your School <no-reply@yourschool.edu>"
APP_URL=https://<your frontend domain>
```

Gmail works too (`smtp.gmail.com:587`) but needs an **App Password**, not your account password.

`APP_URL` is what reset links point at. Get it wrong and every reset email sends users to the wrong place.

### Getting a Resend API key

1. Sign up at [resend.com](https://resend.com) and add your school's domain.
2. Add the DKIM and SPF records it gives you to your DNS, and wait for the
   domain to verify. **`SMTP_FROM` must be on that verified domain** — sending
   as a domain you have not verified gets the mail dropped or spam-foldered,
   which looks exactly like the app being broken.
3. Create an API key. That key is `SMTP_PASS`; the username is literally `resend`.
4. Put the key in your host's secret store, never in a committed file.

### Half-configured relays are rejected on purpose

Startup also refuses a username without a password (or the reverse), and a
`SMTP_FROM` that is not an address. Both would otherwise fail *silently*: sends
are deliberately caught so a failed notification cannot fail the request that
triggered it, so a broken relay produces no visible error — you find out when
somebody cannot get back into their account.

**Delivery has not been tested in this project.** No credentials exist, so no
real email has been sent. Once you set a real relay, verify it end to end by
requesting a password reset and confirming the message arrives in an inbox —
not in the server log.

## Payments

`PAYMENT_PROVIDER` decides how schools pay you. It defaults to `manual`, and
**manual is the only mode that has been verified end to end.**

### Manual (the current default)

Schools pay by bank transfer. A super admin records the payment and extends the
subscription from the Super Admin portal, exactly as before — this flow predates
the billing work and is unchanged.

The admin Billing page detects this mode and shows bank-transfer instructions
instead of a pay button, so nobody is offered a checkout that cannot complete.
Nothing to configure.

### Safepay — chosen, sandbox only, not yet verified

[Safepay](https://getsafepay.pk) settles in PKR and has first-class
subscriptions, so it fits the provider contract without bending it. It was
chosen over PayFast Pakistan because PayFast is transaction-oriented (we would
have to synthesise subscription periods ourselves) and has no official Node SDK.

```
PAYMENT_PROVIDER=safepay
SAFEPAY_API_KEY=<merchant secret>
SAFEPAY_WEBHOOK_SECRET=<webhook secret>
SAFEPAY_ENVIRONMENT=sandbox
```

Plans are matched by token: create each plan in the Safepay dashboard, then
record its token in `Plan.providerPriceIds` as `{"SAFEPAY": "plan_..."}`. The
server resolves the price from our own Plan record, and the webhook resolves the
plan from whatever Safepay actually charged — the browser never chooses a price.

### Sandbox verification — how far it actually got

A sandbox account exists and part of the integration has now been exercised
against real Safepay infrastructure. **The webhook half has not been, and that
is the half that grants paid access.** Treat the adapter as unverified.

**Verified against real Safepay responses**

- Merchant secret authenticates: `POST /client/passport/v1/token` → 200.
- Subscription checkout builds and Safepay accepts it: a real hosted checkout
  URL is returned, carrying the plan token from our own database and the
  institute id as `reference`.
- The plan is resolved server-side. A browser asking for an unknown plan, or one
  with no Safepay token, is refused; asking for nothing falls back to the
  institute's own plan.
- The checkout response contains the URL and nothing else — no key, no customer
  id, no billing state.
- One-time payments complete successfully on Safepay's hosted page.

**Not verified — blocked, not skipped**

- **No webhook has ever been received.** Signature verification, the real
  envelope shape, idempotency, ordering, tenant binding, status transitions,
  `currentPeriodEnd`, invoicing and cancellation are all unproven against real
  traffic. Everything covering them today is a test using a fake provider.
- Whether Safepay's signature covers the raw body (their docs) or
  `JSON.stringify(data)` (their SDK). The adapter follows the SDK. **If the docs
  are right, it will reject every genuine event.** This is the single most
  important thing to settle.
- Whether the envelope really carries `token` and `created_at`. If it does, and
  if the raw body turns out to be signed, switch to them — they are stronger
  than the derived-hash fallback in `safepay.js`.

**Two blockers, both external**

1. *Subscription checkout is unreachable.* Safepay's hosted subscription page
   requires the payer to hold a Safepay account, and sandbox account signup
   fails with `recaptcha_token is required` — their reCAPTCHA does not issue a
   token. Retried in a clean profile. Not worked around, and it must not be.
2. *Webhooks cannot be delivered.* Deliveries were pointed at an ngrok tunnel
   whose TLS certificate is re-signed by a FortiGate appliance on the developer's
   network (`issuer=O=Fortinet, CN=FG181FTK23901319`). Every client that checks
   the chain rejects it. A completed sandbox payment produced zero inbound
   connections at a healthy tunnel.

To resume: use a tunnel that terminates TLS outside the intercepting network
(Cloudflare Tunnel serves a genuine certificate), or test from a different
network — a mobile hotspot confirms the diagnosis in minutes. Then check
Safepay's own **Developers → Endpoints → delivery log**, which distinguishes
"attempted and failed TLS" from "never attempted", the latter meaning the
endpoint is not subscribed to the right events.

`SAFEPAY_CAPTURE_WEBHOOKS` exists for exactly this: it records raw deliveries
before verification so the signing scheme can be settled from real bytes.

Before it can be trusted with money, run these against the sandbox:

- [ ] Does the webhook envelope carry a **unique event id**? The adapter
      currently derives one from the signed bytes, because Safepay signs only
      `data` and an envelope id would be unauthenticated — a replayer could vary
      it to defeat duplicate protection. If a real id exists *inside* the signed
      object, switch to it: identical-payload events would then stay distinct.
- [ ] Does it carry an **authoritative timestamp**? The adapter falls back to
      the subscription's `updated_at`, and to receipt time if that is missing.
      Receipt time orders concurrent redeliveries less precisely.
- [ ] Does **cancel defer to period end**? Their type carries
      `cancel_at_period_end`, but that is inference. If cancel is immediate,
      switch to a pause-at-period-end equivalent — a school that has paid for
      the month keeps the month.
- [ ] Confirm the **customer id** (`user_id`) and **period end**
      (`current_period_end_date`) arrive on the first event.

Only after those pass should you set `SAFEPAY_ENVIRONMENT=production`, which
additionally requires `SAFEPAY_VERIFIED=true` — an explicit acknowledgement that
the checks above were actually run, not a value to set to make startup quiet.

**One structural note on their signature scheme.** Safepay signs
`JSON.stringify(data)`, not the raw request bytes, so **only `data` is
authenticated** — anything in the envelope around it is attacker-controlled. The
adapter therefore reads nothing from the envelope. Do not "improve" it by
pulling an id or timestamp from there.

### Stripe — draft, unusable here

`PAYMENT_PROVIDER=stripe` requires `STRIPE_SECRET_KEY` and
`STRIPE_WEBHOOK_SECRET`. **Stripe does not operate in Pakistan**, so the adapter
exists only as a reference implementation and has never handled real traffic.

Whichever provider you adopt, two rules are structural and must not be relaxed:

- **The return URL proves nothing.** `/billing/pending` says "confirming your
  payment", never "paid". Access changes only on a signature-verified webhook.
- **The webhook route must stay mounted before `express.json()`** in
  `backend/src/app.js`. Signatures are computed over raw bytes; a parsed and
  re-serialised body will not match, and every real event would be rejected.

Point the gateway's webhook at `POST /api/billing/webhook/:provider`. Duplicate
deliveries, out-of-order events and concurrent deliveries are all handled —
see the tests in `backend/tests/billing.test.js`.

### One thing to tidy when you adopt a gateway

`Plan.providerPriceIds` is currently `null` for every plan, and endpoints that
embed a plan in their response (`include: { plan: true }`) therefore send an
empty field to the browser. Populate it and those endpoints will start shipping
your price identifiers to the client.

Price identifiers are not credentials — gateways expect them in client-side
checkout code, and ours grant nothing on their own, because the server resolves
the price from the plan and the webhook resolves the plan from whatever the
gateway actually charged. Nothing is exploitable. But it is untidy, so when you
populate `providerPriceIds`, swap those `plan: true` includes for an explicit
field list that omits it.

## Go-live checklist

**Security**

- [ ] Fresh 48-byte secrets, different from each other
- [ ] Every demo account deleted or repassworded — **the server enforces this**:
      in production it refuses to start if it finds any seeded login, or a super
      admin still using one of the four documented passwords. The likely way they
      arrive is a development dump restored into production, which nothing else
      would have caught
- [ ] `CORS_ORIGIN` set to your real domain — not `*`
- [ ] HTTPS everywhere; `APP_URL` uses `https://`
- [ ] `NODE_ENV=production` (this also hides stack traces from error responses)
- [ ] `SMTP_HOST` and `SMTP_FROM` set — the server will not start without them
- [ ] `PAYMENT_PROVIDER` left at `manual` unless a gateway has been verified end to end

**Data**

- [ ] Point-in-time recovery switched on at the provider — see [Backups](#backups-and-recovery)
- [ ] A restore actually rehearsed at least once — an untested backup isn't a backup
- [ ] `npm run db:backup` runs successfully from wherever you operate the system
- [ ] Each institute's `timezone` set correctly; attendance dates depend on it

**Operational**

- [ ] Health check wired to `/health`
- [ ] Server logs going somewhere you'll actually look
- [ ] `npm test` green in CI before deploys

## Backups and recovery

Attendance, marks and fee records are the school's official record. Losing them
is not an outage, it is a data loss incident — so this section is not optional,
and most of it has to be switched on **at the provider**. No amount of
application code can back itself up.

### 1. Turn on point-in-time recovery (the important bit)

**Neon** — Project → **Settings → Backup & restore**. Set **History retention**
to at least **7 days** (30 on a paid plan if the budget allows). This gives
branch-based restore to any second in the window, which is what you want after
a bad migration or a mistaken bulk delete.

**Render Postgres** (if you use it instead of Neon) — Dashboard → your database
→ **Recovery**. Daily snapshots plus PITR are on for paid instances; **the free
tier has neither**, so a free Render database is not suitable for real school
data.

**Self-hosted / docker-compose** — nothing is automatic. The Postgres data lives
in the `postgres_data` volume, and a `docker compose down -v` destroys it. Run
`npm run db:backup` on a schedule (cron / Task Scheduler) and copy the output
*off that machine*.

### 2. Keep your own dumps as well

Provider recovery protects against your mistakes. It does not protect against a
closed account, a deleted project, or a billing lapse. Keep independent copies:

```bash
cd backend && npm run db:backup          # → backups/educonnect-<timestamp>.dump
```

`pg_dump` only reads, so it is safe against production. It needs the PostgreSQL
client tools on `PATH` (on Windows, something like
`C:\Program Files\PostgreSQL\18\bin`).

Store them somewhere that is not the database host, keep at least 7 daily and
4 weekly, and remember a dump of a school's database is **personal data about
children** — encrypt it at rest and restrict who can read it.

**Always take one immediately before running `npx prisma migrate deploy`.**

### 3. Know what you have

```bash
cd backend && npm run db:verify
```

Read-only. Prints a per-table row count, the newest update in each table, and a
fingerprint. Capture it before a backup; compare after a restore. Matching
fingerprints mean the restore is complete.

### Restoring — the drill

Rehearse this **before** you need it, into a scratch database, never over a live
one.

> **The rehearsal is automated.** `npm run db:restore-check` does the whole
> thing — fingerprints the live database, takes a dump, restores it into a
> freshly named scratch database, fingerprints that, compares the two, and
> drops the scratch whether it passed or failed. It never writes to the live
> database, and refuses to run at all if the scratch name it generated somehow
> matched the live one.
>
> ```
> live      eb5c60aeae467128  (64793 rows)
> restored  eb5c60aeae467128  (64793 rows)
> ✓ FINGERPRINTS MATCH
> ```
>
> Run it while nothing is writing: the fingerprint is taken just before the
> dump, so a write in between makes an honest restore look wrong.
>
> The steps below are what it automates, and what you would do by hand
> against a managed host that dumps for you.

1. **Stop writing.** Scale the API to zero, or put it in maintenance. A restore
   while requests are landing produces a database that matches nothing.
2. **Record the damage.** Note the last-known-good time; capture
   `npm run db:verify` output from the broken database if it still responds.
3. **Restore into a NEW database, never over the live one.**
   - *Neon*: create a branch from the timestamp — Restore → pick the point in
     time. This is non-destructive; the original branch stays.
   - *From a dump*:
     ```bash
     createdb educonnect_restore
     pg_restore --no-owner --no-privileges --dbname educonnect_restore backups/<file>.dump
     ```
4. **Verify before switching.** Point `DATABASE_URL` at the restored copy and
   run `npm run db:verify`. Compare against the fingerprint you captured. Sign
   in as one real user and check their data looks right.
5. **Cut over** by changing `DATABASE_URL` and restarting the API. Keep the
   damaged database until you are certain — it is evidence.
6. **Afterwards**, write down what was lost between the restore point and the
   incident. Someone will ask.

> **Never** use `npm run db:reset`, `db:push` or `db:seed` to "fix" production.
> They are blocked when `NODE_ENV=production` for exactly this reason. The only
> schema command production runs is `npx prisma migrate deploy`.

## Handling real student data

This is worth thinking about before a real school uses it, not after.

- **Minimise.** The schema already avoids storing what it doesn't need. Don't add fields you have no use for.
- **Access is already narrow.** Teachers see only students they teach, parents only their own children, and the API enforces this — the client never filters for security. `backend/tests/tenancy.test.js` proves it.
- **Audit.** Every mutation writes to `audit_logs` with the user, institute, action and IP.
- **Deletion is recoverable.** Institutes, students, teachers and parents are soft-deleted: they disappear from the app but the rows survive, restorable from the recycle bin. Only `DELETE /api/institutes/:id/purge` is permanent, and it refuses to run unless the institute has already been deleted — two deliberate steps.
- **Legal.** Student records are personal data about minors. Check what your jurisdiction requires for consent, retention and breach notification. That's a policy question this codebase can't answer for you.

## Troubleshooting

**`Refusing to start in production with insecure settings`**
Working as intended — read the listed items and fix them.

**`Cannot reach the database`**
Check `DATABASE_URL` and, on a managed host, that `?sslmode=require` is present.

**Frontend loads but every API call fails with CORS**
`CORS_ORIGIN` must exactly match your frontend origin, scheme included, no trailing slash.

**Login works, then everything 401s a few minutes later**
`JWT_ACCESS_SECRET` differs between instances, or the API restarted with a different value. Set it explicitly rather than letting a platform regenerate it.

**Login succeeds but the session vanishes on reload**
The refresh cookie isn't reaching the API. On split domains set `COOKIE_CROSS_SITE=true` and serve both sides over HTTPS; check `CORS_ORIGIN` matches the frontend origin exactly.

**Prisma complains about a column that clearly exists**
The generated client is stale. Run `npx prisma generate` and restart — file watchers don't see changes inside `node_modules`.

**Attendance saving to the wrong day**
The institute's `timezone` is wrong. Set it to a real IANA zone such as `Asia/Karachi`.
